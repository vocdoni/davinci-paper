At the core of \davinci lie a set of arithmetic circuits that enforce the correctness of every step of the election. Each circuit corresponds to a distinct task and, taken together, they guarantee that all protocol rules are satisfied without revealing any private information. Specifically, the \emph{ballot circuit} (Section~\ref{sec:vocdoni-protocol:circuits:ballot}) ensures that encrypted votes are valid and well-formed, the \emph{verifier circuit} (Section~\ref{sec:vocdoni-protocol:circuits:verifier}) verifies the voter's census membership; the \emph{aggregation circuit} (Section~\ref{sec:vocdoni-protocol:circuits:aggregation}) combines multiple authenticated votes into a single proof; and the \emph{state transition circuit} (Section~\ref{sec:vocdoni-protocol:circuits:state-transition}) updates the global state root and produces the \ac{ZK-SNARK} proof that is verified on-chain. The flow of these circuits and their interactions is shown in Figure~\ref{fig:circuits-flow}. {\color{blue}Add \textit{results} circuit.}

For clarity, the circuits are described in this section with their full set of public inputs explicitly listed. In the actual implementation, however, we apply an optimization: rather than exposing all public inputs $PI$ individually, we compute a single commitment $h = Hash(PI)$ and use $h$ as the only public input. The proof verifier then checks that $Hash(PI) = h$, ensuring that the original public inputs are consistent while reducing both proof size and verification cost. In \davinci, this commitment is computed using the MiMC-7 hash function {\color{blue}(use hlget to point "Hash" to MiMC-7)}. Note that this optimization does not alter the semantics of the circuits but significantly reduces verifier complexity and on-chain verification costs. Other implementation aspects such as the exact number of constraints and the proving frameworks used are deferred to Section~\ref{sec:analysis:implementation}.

\subsubsection{Ballot circuit} 
\label{sec:vocdoni-protocol:circuits:ballot}

The ballot circuit (\hlset{\ballotcircuit}), illustrated in Figure~\ref{fig:circuit-ballot}, is generated locally by the voter at the time of casting a ballot. Its purpose is twofold: first, to prove that the encrypted ballot is valid and complies with the protocol rules defined by the organizer; and second, to prove that the vote identifier (\voteid) has been correctly derived. The correctness of this circuit is attested by a \ac{ZK} proof generated using the \ac{ZK-SNARK} protocol described in Section~\ref{sec:cryptographic-primitives:zkp}, instantiated over the BN254 curve. We call the resulting proof \textit{ballot proof} and denote it as $\hlset{\ballotproof}$. We detail below the inputs and constraints of the ballot circuit. 

\begin{spacing}{1.25}
	\vspace{0.3cm}
	\noi \textbf{Public inputs}
	\begin{itemize}
		\item $\public$ $\processid$: election identifier. 
		\item $\public$ $\ballotmode$: ballot protocol configuration.
		\item $\public$ $\epk$ ($EPK$): encryption public key.
		\item $\public$ $\address$: voter's address.
		\item $\public$ $\weight$: voter's weight.
		\item $\public$ $\encryptedballot$: encrypted ballot. 
		\item $\public$ $\voteid$: vote's unique identifier. 
	\end{itemize}
	\textbf{Private inputs}
	\begin{itemize}								
		\item \private $\ballot$: plaintext voter's voting choice.
		\item \private $k$: random scalar.
	\end{itemize}
	\textbf{Constraints}
	\begin{itemize}								
		\item \emph{Vote encryption}. Correct encryption of the ballot: $\encryptedballot = \hlget{\Enc}_{\epk}(\ballot; k).$
		\item \emph{Protocol rules compliance}. The ballot meets the protocol rules (number of valid choices, etc.): $... + \weight$.
		\item \emph{Vote identifier}. The vote's identifier is correctly computed: $\voteid = \text{Hash} (\processid \conc  \address \conc k).$
	\end{itemize}
	\vspace{-0.3cm}
\end{spacing}

\subsubsection{Verifier circuit}
\label{sec:vocdoni-protocol:circuits:verifier}

The verifier circuit (\hlset{\verifiercircuit}), illustrated in Figure~\ref{fig:circuit-verifier}, is generated by the sequencer when processing a vote. This circuit verifies the ballot's proof generated by the voter and it also validates the voter’s eligibility in the census and the correctness of their digital signature. The correctness of this circuit is attested by a ZK proof generated using the ZK-SNARK protocol described in Section~\ref{sec:cryptographic-primitives:zkp}, instantiated over the BLS12-377 curve. We call the resulting proof the \textit{authentication proof} and denote it as $\hlset{\authenticationproof}$. We detail below the inputs and constraints of this circuit. {\color{blue}-- Authentication of verification proof?}

\begin{spacing}{1.25}
	\vspace{0.3cm}
	\noi \textbf{Public inputs}
	\begin{itemize}
		\item \public $\processid$: election identifier.
		\item \public $\ballotmode$: ballot protocol configuration.
		\item \public $\epk$ ($EPK$): encryption public key.
		\item \public $\encryptedballot$: encrypted ballot.		
		\item \public $\voteid$: voter's identifier.
		\item \public $\address$: voter's address.
		\item \public $\weight$: voter's weight.
	\end{itemize}
	\textbf{Private inputs}
	\begin{itemize}		
		\item \private $\pk$: voter's public key.						
		\item \private $\signature$: voter's signature.
		\item \private $\ballotproof$: voter's ballot proof.
	\end{itemize}
	\textbf{Constraints}	
	\begin{itemize}
		\item \emph{Voter's proof verification.} The voter's submitted proof is valid for the inputs provided: 
		$$\hlget{\PVerify}\left(\ballotproof, PI = (\processid, \ballotmode, \epk, \encryptedballot, \voteid, \weight)\right) = \true.$$
		\item Compute the address derived from the user's public key: $ \address = \hlget{\Keccak}(\pk)$.
		\item \emph{Authentication + non-malleability.} The signature of the vote's identifier is valid for the given public key:
		$$ \hlget{\SVer}_{\pk}(\voteid, \signature) = \true. $$
	\end{itemize}
	\vspace{-0.3cm}
\end{spacing}

\subsubsection{Aggregation circuit}
\label{sec:vocdoni-protocol:circuits:aggregation}

The aggregation circuit (\hlset{\aggregationcircuit}), illustrated in Figure~\ref{fig:circuit-aggregate}, is generated by the sequencer to combine multiple authenticated votes into a single proof. Its purpose is to reduce verification overhead by recursively aggregating individual authentication proofs, while ensuring that all aggregated votes belong to the same election.  The batch size, i.e., the maximum number of proofs aggregated in a single execution, is a fixed parameter (currently set to 60). If fewer proofs are available, the sequencer pads the batch with dummy proofs so that the circuit always operates on a fixed-size input. The correctness of this circuit is attested by a ZK proof generated using the \ac{ZK-SNARK} protocol described in Section~\ref{sec:cryptographic-primitives:zkp}, instantiated over the BW6-761 curve. We call the resulting proof the \textit{aggregation proof} and denote it as $\hlset{\aggregationproof}$. We detail below the inputs and constraints of the aggregation circuit.  

\begin{spacing}{1.25}
	\vspace{0.3cm}
	\noi \textbf{Public inputs}
	\begin{itemize}
		\item \public $\encryptedballot_i$: list of voters' encrypted ballots.
		\item \public $\voteid_i$: set of vote's identifiers.
		\item \public $\address_i$: list of voters' addresses.
		\item \public $\processid$: election identifier.
		\item \public $\ballotmode$: ballot protocol configuration.
		\item \public $\epk$ ($EPK$): encryption public key.
	\end{itemize}
	\textbf{Private inputs}
	\begin{itemize}								
		\item \private $\authenticationproof_i$: set of authentication proofs.
	\end{itemize}
	\textbf{Constraints} \\ \vspace{-0.4cm}		
	\begin{itemize}
		\item \emph{Votes aggregation.} The accumulated authentication proofs are valid (for the given inputs). For every $i$:
		$$\hlget{\PVerify}\left(\authenticationproof, \publicinputs = (\encryptedballot_i, \voteid_i, \address_i, \processid, \ballotmode, EPK)\right) = \true.$$
		\item \emph{Shared public inputs.} The public inputs \processid, \ballotmode, \epk, and \censusroot are the same for all proofs.
	\end{itemize}
	\vspace{-0.3cm}
\end{spacing}

\end{figure}

\subsubsection{State transition circuit} 
\label{sec:vocdoni-protocol:circuits:state-transition}

The state transition circuit (\hlset{\statetransitioncircuit}), illustrated in Figure~\ref{fig:circuit-state-transition-v2}, is generated by the sequencer to update the global state of the election. Its purpose is to verify that a batch of aggregated votes has been correctly incorporated into the state Merkle tree, that overwrites and vote identifiers are handled consistently, and that the accumulators of encrypted results are updated accordingly. The correctness of this circuit is attested by a \ac{ZK} proof generated using the \ac{ZK-SNARK} protocol described in Section~\ref{sec:cryptographic-primitives:zkp}, instantiated over the BN254 curve, which is supported by Ethereum’s native precompiles for proof verification. We call the resulting proof the \textit{state proof} and denote it as $\hlset{\stateproof}$. This proof is submitted on-chain and verified by the process management smart contract, ensuring that every accepted state transition complies with the protocol rules.

To formalize the setting, let the sequencer collect a batch of $N$ votes ($N<60$), of which $n$ are new submissions and $m = N-n$ are overwrites of previously cast ballots. In the following, we describe the inputs and constraints of the state transition circuit in detail.


\begin{spacing}{1.25}
	\vspace{0.3cm}
	\noi \textbf{Public inputs}
	\begin{itemize}
		\item \public $\censusroot$: census Merkle tree root.
		\item \public $\stateroot^{old}$: current state tree root.
		\item \public $\stateroot^{new}$: new tree root after all state transitions are applied.
		\item \public $\numoverwrites^{old}$: current number of overwrites.
		\item \public $\numoverwrites^{new}$: number of overwrites after all state transitions are applied.
		\item \public $\numvotes^{old}$: current number of votes.
		\item \public $\numvotes^{new}$: total number of votes after all state transitions are applied.
		\item \public $C$: commitment to the data blob.
	\end{itemize}
	\textbf{Private inputs}
	\begin{itemize}			
		\item \private $\censusorigin$: census origin parameter.	
		\item \private $\{\aggregationproof_i\}_{i= 1}^{N}$: set of aggregation proofs.
		\item \private $\{\censuspf_i\}_{i = 1}^N$: census membership proofs.
		\item \private $\ballotmode$: ballot protocol configuration.
		\item \private $EPK$: encryption public key.
		\item \private $\processid$: election identifier.
		\item \private $\{\voteid_i\}_{i= 1}^{N}$: set of vote's identifiers.
		\item \private $\{\encryptedballot_i\}_{i= 1}^{N}$: set of voters' encrypted ballots.
		\item \private $\{\pk_i\}_{i= 1}^{N}$: list of voters' public keys.
		\item \private $\{\merkleproofs^{encBallots}_i\}_{i= 1}^{N}$: Merkle tree proofs of encrypted ballots. If it is a new vote, the proof will be a non-inclusion proof, if it is an overwrite, an inclusion proof.
		\item \private $\{\merkleproofs^{\voteid}_i\}_{i= 1}^{N}$: non-membership proofs of vote identifiers.
		\item \private $\addaccumulator^{old}$: current accumulator of votes (before the transitions).
		\item \private $\substractaccumulator^{old}$: current accumulator of votes that have been overwritten (before the transition).
		\item \private $k$: random scalar.
		\item \private $\openproof$: KZG opening proof.
	\end{itemize}
	\textbf{Constraints} \\ \vspace{-0.4cm}		
	\begin{itemize}
		\item \emph{Aggregation verification.} The accumulated authentication proofs are valid. For every $i\in\{1,\dots,N\}$:
		$$\hlget{\PVerify}(\authenticationproof, PI = (\encryptedballot_i, \voteid_i, \pk_i, \processid, \ballotmode, EPK, \censusroot)).$$
		\item \emph{Census membership.} The address derived from the user's public key is part of the census, and verifies the census proof with the user's weight provided:
		$$ \hlget{\censusTree}.\hlget{\MTVerify}\left(\weight, \address, \censuspf, \censusroot\right) = \true. $$
		\item \emph{Transition verification.} Verify initial state and state transitions are applied correctly.
				\begin{itemize}
					\renewcommand{\labelitemii}{$\circ$}
					\item Verify that the inputs $\processid$, $\censusroot$, $\ballotmode$, $\epk$, $\addaccumulator$, and $\substractaccumulator$ correspond to the content of the census Merkle tree leaves $\texttt{0x0}$, $\texttt{0x1}$, $\texttt{0x2}$, $\texttt{0x3}$, $\texttt{0x4}$, $\texttt{0x5}$, respectively. {\color{blue} The root of the tree, with all data and those six leaves, results in \stateroot.}
					\[\stateTree\text{(with these six leaves and the rest)}.\MTRoot() = \stateroot.\]
					\item Verify that none of the $\voteid_i$ for all $i\in\{1,\dots,N\}$ are initially part of the tree:
					\[\stateTree.NonInclusionVerify(\voteid_i, \merkleproofs^{\voteid}_i, \stateroot).\] 
					\item Ensure that new votes are not part of the tree yet. For $i = 1, \dots, n$:
					\[\stateTree \text{-- the leaf following the $\address_i = \hlget{\Keccak}(\pk_i)$ path is empty}.\] 
					\item Ensure that overwrites do correspond to votes that were already on the tree. For $i = n+1, \dots, N$:
					\[\stateTree \text{-- the leaf following the $\address_i = \hlget{\Keccak}(\pk_i)$ path stores an encrypted ballot}.\] 
					\item State transitions.
					\begin{itemize}
						\item For new votes (keep iterating for all of them):
							\begin{enumerate}
								\item Add encrypted ballot to the tree: $\stateTree.\hlget{\MTInsert}(\address = \hlget{\Keccak}(\pk), \encryptedballot)$.
								\item Add vote identifier: $\stateTree.\hlget{\MTInsert}(\voteid)$.
								\item Increase votes counter: $\numvotes = \numvotes + 1$.
								\item Aggregate the vote to the results accumulator: $\addaccumulator = \addaccumulator + \encryptedballot$.
						\end{enumerate}
						\item For overwritten votes (keep iterating for all of them):
							\begin{enumerate}
								\item Overwrite the encrypted ballot: $\stateTree.\hlget{\MTUpdate}(\address = \hlget{\Keccak}(\pk), \encryptedballot)$.
								\item Add vote identifier: $\stateTree.\hlget{\MTInsert}(\voteid)$.
								\item Increase votes counter: $\numvotes = \numvotes + 1$.
								\item Increase overwrites counter: $\numoverwrites = \numoverwrites + 1$.
								\item Aggregate the vote to the results accumulator: $\addaccumulator = \addaccumulator + \encryptedballot$.
								\item Aggregate the old vote to the accumulator: $\substractaccumulator = \substractaccumulator + \encryptedballot^{old}$.
							\end{enumerate}
						{\color{blue}The old  $\encryptedballot^{old}$ should also be inputs or retrieved from the MT inclusion proofs.}
					\end{itemize}
					\item After all previous state transitions are done, recompute new tree root:
					\[\stateroot^{new} = \stateTree.\hlget{\MTRoot}().\]
					\item Reencrypt all leafs of the tree (both old and new ones). {\color{blue}New are ok, but for those that are old, also verify MTProofs of membership?}.
					\[newLeafContent = \hlget{\ReEnc}_{\epk}(\encryptedballot_i, k), \quad k = Hash(k).\]
				\end{itemize}
	\item \emph{Data blob}. 
		\begin{itemize}
			\item Construct blob $B$ (as described in Section~X).
			\item Derive polynomial $p(x)$ from $B$.
			\item Compute evaluation point
					\( z = \hlget{\Poseidon}(\processid, C, \openproof) \).
			\item Compute evaluation \(y = p(z)\).
			\item Verify  
			\(\hlget{\CVerify}(z, y, C, \openproof) = \true.\)\\
		\end{itemize} 
	\end{itemize}
	\vspace{-0.3cm}
\end{spacing}

{\color{blue}Mention that an advantage of splitting the circuits of the sequencers in 3 is that if the stateRoot changes in the meantime, the sequencer only needs to rerun the last circuit and not all three of them.}\\
